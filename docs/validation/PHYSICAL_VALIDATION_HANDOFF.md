# Daily Town physical validation handoff

This is the human-facing handoff for the remaining Android MVP physical gates on PR #10.

## What the human needs to return

The minimum review package is:

1. the untouched physical marker evidence ZIP generated by `tools/android/run_naver_physical_evidence.sh`;
2. the separately completed `marker-promotion-approval.v1.json` from the same evidence directory;
3. the final cumulative field-test structured JSON exported after the fourth session;
4. the generated `<final-export>.review.md` and `<final-export>.collection-plan.txt` when available;
5. one short usability note per session (plain text is enough).

Do not commit any of these physical/session-derived files to GitHub.

## Fixed test conditions

Use the same real Android phone and the same PR #10 commit for the whole pilot.

- tracking preset: `BALANCED`;
- test order: Seoul NEW_AREA -> Seoul REPEAT_AREA -> Jungwon-gu NEW_AREA -> Jungwon-gu REPEAT_AREA;
- do not clear app data between a NEW_AREA session and its paired REPEAT_AREA session;
- each session: at least 600 seconds;
- enter the NAVER walking-route reference distance before each session;
- export before closing/force-stopping the app;
- keep credentials in environment variables only.

## Step 1 — prepare the shell and phone

Connect exactly one authorized real Android phone with USB debugging enabled.

```bash
adb devices -l
```

Set both credentials without printing their values:

```bash
read -rsp "NAVER_MAP_NCP_KEY_ID: " NAVER_MAP_NCP_KEY_ID; echo; export NAVER_MAP_NCP_KEY_ID
read -rsp "TOUR_API_SERVICE_KEY: " TOUR_API_SERVICE_KEY; echo; export TOUR_API_SERVICE_KEY
```

Run the full physical preflight:

```bash
bash tools/field_test/prepare_physical_test.sh
```

Do not start the pilot if preflight fails.

## Step 2 — collect physical marker evidence

Run:

```bash
bash tools/android/run_naver_physical_evidence.sh
```

The runner must finish with an integrity-verified physical evidence directory and ZIP. Keep the generated ZIP unchanged.

Review the physical phone and the 28 captures using `REVIEW.md`. Only mark a check `PASS` when it was actually observed:

- `marker_readability`: marker labels/symbols are readable outdoors and do not collapse into the map;
- `selected_state_anchor`: the selected marker state clearly anchors the selected place;
- `route_hud_companion_readability`: route/HUD/companion content remains readable together with the map;
- `provider_road_place_comprehension`: NAVER roads/place labels remain understandable under the app overlay;
- `naver_attribution_legal_ui`: NAVER attribution/legal UI stays visible and unobstructed.

In the generated evidence directory, edit only the separate `marker-promotion-approval.v1.json` review fields:

- set each observed check to `PASS` or leave it `PENDING`/`FAIL`;
- set `reviewer`;
- set `reviewed_at`;
- set `decision` to `APPROVED` only when all five checks are `PASS`.

Do not replace fingerprint/session SHA fields and do not reuse an approval file from another run.

Return the original generated ZIP plus the completed approval JSON separately.

## Step 3 — run the four field sessions

Before the first session, open Settings and confirm the canonical POI source is `한국관광공사 TourAPI`.

For every session:

1. confirm map status is READY and current-location overlay is at the real location;
2. confirm tracking preset is BALANCED;
3. choose the correct `NEW_AREA` or `REPEAT_AREA` profile;
4. check the planned walking route in NAVER and enter its total walking distance in meters;
5. start actual-location tracking;
6. walk normally for at least 10 minutes — do not alter behavior just to make metrics pass;
7. stop tracking;
8. review the session checklist and record the current session in comparison;
9. export structured JSON before app termination;
10. write one short usability note.

Run in this exact order:

1. Seoul — NEW_AREA
2. Seoul — REPEAT_AREA
3. Jungwon-gu — NEW_AREA
4. Jungwon-gu — REPEAT_AREA

Do not clear app data between sessions 1 and 2, or between sessions 3 and 4.

## Step 4 — handle exports correctly

Keep the export after each session as a local safety snapshot, for example:

- `01-seoul-new.json`
- `02-seoul-repeat.json`
- `03-jungwon-new.json`
- `04-jungwon-repeat-final.json`

Sequential exports can contain overlapping previously recorded sessions. Therefore, do **not** automatically aggregate all four snapshots as if they were independent batches.

The export produced after session 4 is the canonical handoff when it contains the complete four-session comparison history.

Run the final offline review against that final export:

```bash
bash tools/field_test/review_physical_export.sh 04-jungwon-repeat-final.json
```

Optional strict readiness check:

```bash
python3 tools/field_test/review_packet.py \
  04-jungwon-repeat-final.json \
  --format summary \
  --require-evidence-ready
```

If `python3` is not a working command in Git Bash, use the same working Python command reported by the physical preflight (`python`, or `py -3`).

## Step 5 — what to observe during the walks

Do not stop a valid session only for small GPS drift, temporary map loading, a missed encounter, or a slightly late companion reaction. Record meaningful defects instead.

Especially note:

- current-location trust: stale jump, obvious GPS drift, or wrong-place marker;
- POI quality: duplicate same-place markers, stale markers, wrong physical placement, severe clutter;
- map readability: route/roads/place names hidden by overlays;
- companion presence: useful and visible vs. distracting or absent;
- encounter pacing: too sparse, too dense, or hard to understand;
- repeat fatigue: whether the repeat route feels meaningfully different/useful or simply repetitive;
- battery/heat: unexpected heat or drain that makes normal use uncomfortable;
- accessibility/usability: controls hard to see, reach, understand, or use while walking.

A short note such as `Seoul REPEAT: map readable; two duplicate POIs near X; companion reaction felt late; phone mildly warm; repeat fatigue medium` is enough.

## Provisional acceptance baseline

The current pilot baseline is:

- session duration >= 600 seconds;
- GPS rejection <= 15%;
- map health = READY;
- distance error <= 15%;
- battery drain <= 12 percentage points/hour;
- discovered encounters >= 2/session;
- encounter resolution >= 50%;
- REPEAT_AREA fatigue proxy <= 40%;
- two NEW_AREA + two REPEAT_AREA sessions;
- matching tracking preset and all required comparison evidence.

Passing these thresholds makes the evidence ready for product review; it does not automatically approve marker promotion, PR merge, beta release, or product quality.

## Exact handoff checklist

Send these files/results back for review:

- `physical-<timestamp>.zip` — unchanged marker evidence archive;
- completed `marker-promotion-approval.v1.json` — separate from the ZIP;
- final cumulative field-test JSON after session 4;
- generated `.review.md` and `.collection-plan.txt` if the review command succeeded;
- four short usability notes in the same message or a small text file.

The earlier three field-test JSON snapshots are backup evidence. Send them only if the final export is missing sessions or a problem needs debugging; otherwise the final cumulative export is sufficient for the normal review path.
